# Junction 2026 working instructions

- Read the relevant project docs before brainstorming, planning, choosing a stack or editing code. Start with [status](docs/STATUS.md), then check the [project](docs/PROJECT.md) and [team](docs/TEAM.md) when they affect the task.
- Use [challenges](docs/CHALLENGES.md) for competition fit, rules and submissions. Use [software](docs/SOFTWARE.md) and [hardware](docs/HARDWARE.md) for stack and prototype decisions. Check [resources](docs/RESOURCES.md) before recommending APIs, platforms or sponsor tools.
- Fit the build to the available hours and aim for a working end-to-end demo. Prefer tools the team can already run and equipment the team can actually access. Use the simplest design that meets the confirmed requirements.
- Label verified facts, assumptions and unknowns. Never invent challenge requirements, API access, installed software or on-site equipment. Record the source and verification date when adding external facts.
- Update the relevant docs when you verify something new. Update [status](docs/STATUS.md) after meaningful milestones and log significant technical decisions and rationale in [decisions](docs/DECISIONS.md).
- Team members pull from GitHub before starting new tasks. Read the current local files, and commit and push documentation changes via the [team workflow](README.md#work-together) so others can pull them.
- Never commit secrets, credentials, tokens, or private keys.
